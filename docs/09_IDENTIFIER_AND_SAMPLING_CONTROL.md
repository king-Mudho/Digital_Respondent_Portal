# 09 — Identifier scheme & sampling control

This closes the gap flagged in the GigaFood Africa QC review (September 2026): the v1.0
blueprint referenced Master_ID/Sample_ID everywhere but never specified their format,
which blocked its own Section 22 Step 1 ("freeze the identifier schema"). This document
is that specification.

## Identifier scheme

### Master_ID — permanent organisation identifier

Format: `MID-<province-code(2)>-<sequence(6)>`, e.g. `MID-HA-000418`.

- Generated by the system at organisation import, never user-entered.
- Immutable for the life of the organisation record, independent of whether it is
  currently a Main, Reserve, activated-Reserve, or later re-sampled case.
- `province-code` is the two-letter code from the frozen province lookup table (seeded
  with `StratumDefinition`); `sequence` is a zero-padded, database-assigned monotonic
  integer, unique within the province code — collision is structurally impossible
  because the sequence is DB-generated, not derived from any external input.
- Human-readable enough to read aloud over the phone or SMS if needed, but never used as
  a secret (see `10_INVITATION_AND_CONSENT.md` — the invitation token, not the
  Master_ID/Sample_ID, is the access-control boundary).

### Sample_ID — sampling-instance identifier

Format: `SID-<year(4)>-<sequence(6)>`, e.g. `SID-2026-000418`.

- One `Organisation` (one Master_ID) has exactly one active `SampleCase` (one Sample_ID)
  per study wave. If the organisation is re-sampled in a later wave or study, a new
  Sample_ID is issued against the same Master_ID — the historical case is never
  overwritten.
- `sequence` is DB-generated at `SampleCase` creation (at Main-400/Reserve-400 import
  time), unique within `year`.
- A Main case and its matched Reserve case are two distinct `SampleCase` rows (two
  distinct Sample_IDs), linked via `SampleCase.matched_case` — this is what lets the
  system enforce the reserve lock as a query condition rather than a manual list.

### Generation point and uniqueness rule

Both identifiers are generated exclusively by the `sampling` app's import routine at
Main-400/Reserve-400 load time (Phase 0/1 of `27_AGENT_EXECUTION_PLAN.md`), never typed
in by a user and never derived from personal data (no name/phone-number encoding). This
guarantees uniqueness by construction (single writer, DB sequence) rather than requiring
a collision-detection routine.

## Main-400 / Reserve-400 control

Sample integrity is a database-level control, not a spreadsheet convention (the
strongest design decision carried over unchanged from the v1.0 blueprint).

- `SampleCase.sample_type = MAIN` records can be verified, contacted and invited.
- `SampleCase.sample_type = RESERVE` records are visible only to
  `IsFieldCoordinatorOrAdmin` users and cannot receive an invitation while
  `status = LOCKED` — enforced in `sampling.services.is_invitable()`, called by every
  invitation-issuing code path (`AGENTS.md` ground rule 4).
- Each Main record stores its matched Reserve via `SampleCase.matched_case`.
- Reserve activation requires one of the authorised reasons: `INELIGIBLE`, `INACTIVE`,
  `DUPLICATE`, `REFUSAL`, `NONRESPONSE_EXHAUSTED` (after the approved follow-up
  sequence in `12_CONTACT_CRM_AND_MESSAGING.md`).
- Activation always writes `activated_by`, `activated_at`, `activation_evidence_note`,
  and an `AuditEvent` in the same transaction — never as separate, potentially-skipped
  steps.
- Convenience replacement, geographic substitution, or replacing a difficult respondent
  simply because the reserve is easier to contact is blocked by both interface design
  (no "swap" button outside the activation flow) and by requiring one of the five
  authorised reasons above — there is no free-text "other" escape hatch.

## Workflow status engine (S00–S16)

Each Main organisation has exactly one `SampleCase.workflow_status`:

| Code | Status |
|---|---|
| S00 | Selected Main |
| S01 | Verification required |
| S02 | Organisation verified |
| S03 | Eligible respondent identified |
| S04 | Invitation prepared |
| S05 | Invitation sent |
| S06 | Invitation opened |
| S07 | Survey started |
| S08 | Survey submitted |
| S09 | QA query |
| S10 | QA passed |
| S11 | Completed |
| S12 | Refused |
| S13 | Nonresponse |
| S14 | Ineligible |
| S15 | Duplicate/inactive |
| S16 | Reserve eligible for activation |

Implemented as a database enum with an explicit state-transition table in
`sampling/services.py` (not a free-text field) — invalid transitions (e.g. `S02` →
`S08` without passing through consent) are rejected server-side and logged as an
`AuditEvent` if attempted. `S12`–`S15` are the terminal states that make a case
`S16`-eligible for reserve activation, subject to the approved follow-up sequence having
been exhausted first.

## Workflow advancement from events (2026-09-14)

Until this date a case reached S05 when invited and never moved again. It now follows its
respondent, one legal transition at a time and forward only
(`sampling.services.advance_case_on_respondent_event` / `advance_case_on_qa_outcome`):

| Event | Case moves to |
|---|---|
| Invitation link opened (validated) | S06 |
| Questionnaire link handed over (`/kobo/redirect-url/`) | S07 |
| Kobo submission reconciled (walks S05/S06 → S08 for a KoboCollect submission) | S08 |
| Automated QA flag, or a human QUERY | S09 |
| Human QA ACCEPT | S10 |
| Withdrawal recorded (from S05–S07) | S12 |

S01–S03 are never inferred: a case invited while still at S00–S02 keeps its status (the
case page says so before inviting). Coordinators move cases through verification in bulk
from the Main-400 register (`/sample-cases/bulk-transition/`, S00→S01→S02→S03 only, each
case audited). S13 Nonresponse now requires every reminder in the sequence to have been
**sent** for the live invitation (`12_CONTACT_CRM_AND_MESSAGING.md`).
